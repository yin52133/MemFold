# 04 Dreaming And Retention

## 1. 这份文档讲什么

这里只讲一个核心问题：

工作记录里的信息，什么时候能进入长期记忆，什么时候只能继续观察，什么时候必须隔离，什么时候应该直接丢掉。

如果这个问题说不清，dreaming 就会从“整理器”变成“噪音制造器”。

## 2. Dreaming 的职责

Dreaming 只做四选一决策：

1. 保留到长期记忆
2. 暂存继续观察
3. 隔离等待复核
4. 直接丢弃

它不负责：

- 自由总结
- 生成新事实
- 把所有工作记录都升成长期记忆

## 3. 输入边界

Dreaming 只能消费：

- 可晋升的工作记录
- 安全清洗后的历史档案摘要
- 现有长期记忆的比较项

不能直接消费：

- 分析草稿
- 原始敏感正文
- `sterile` 模式下默认产生的临时记录

## 4. 四种决策

### 4.1 保留

进入长期记忆的条件必须严格。第一版建议至少满足下面之一：

- 用户明确说“记住这个”
- 这是稳定用户偏好
- 这是稳定项目约束
- 同一条信息跨多个 session 重复出现，且多次使用后没有被纠正

### 4.2 暂存

以下情况只留在工作记录继续观察：

- 只出现过一次
- 当前看起来有用，但还没跨 session 复现
- 证据不足以说明它是长期信息

### 4.3 隔离

以下情况进入隔离区，不允许自动参与后续长期晋升：

- 和现有长期记忆冲突
- 用户明确说“这个不对”
- 证据链互相矛盾
- 敏感性判断不明确

### 4.4 丢弃

以下情况直接丢弃：

- 明显一次性任务状态
- 单次推理过程
- 无法验证的猜测
- 纯分析草稿
- 含敏感原文且无法安全清洗

## 5. Dreaming 的流程

```text
收集候选
  -> 去重
  -> 聚类
  -> 看是否跨 session 复现
  -> 看是否与现有长期记忆冲突
  -> 做出四选一决策
  -> 写解释
  -> 更新长期记忆 / 隔离区 / 丢弃记录
```

这里最重要的不是“模型分数”，而是：

- 输入是否干净
- 规则是否清楚
- 错误是否能回滚

## 6. 为什么分析草稿不能参与晋升

分析草稿是系统自己的临时解释区。

如果允许它直接晋升，就会出现：

```text
系统猜了一次
  -> 把自己的猜测记下来
  -> 再把这个猜测升成长期记忆
```

这就是自我污染。

所以规则必须写死：

- 分析草稿不能进入工作记录
- 分析草稿不能直接进入长期记忆
- 分析草稿只能帮助解释，不帮助记住

## 7. 为什么错误记忆不能只靠 status 挡

只给一条错误记忆打 `rejected`，是不够的。

系统会这样失败：

```text
原错误记忆 A 被 reject
  -> 换个 summary 变成 B
  -> 系统把 B 当新东西
  -> 又自动晋升
```

所以需要语义墓碑：

- `claim_fingerprint`
- `tombstones`

它们的作用不是装饰，而是防止同一个错误 claim 换壳复活。

## 8. 验收

### 8.1 错误记忆不可复活

失败样例：

- 换 summary 重新晋升
- 换证据重新晋升

通过门槛：

- 被 tombstone 命中的 claim 自动晋升率为 0

### 8.2 Dreaming 不自我污染

失败样例：

- 分析草稿被当成正式记录晋升

通过门槛：

- 纯分析输入的晋升率为 0

### 8.3 敏感信息不入库

失败样例：

- token / cookie / private key 出现在 JSONL、Markdown、SQLite、QMD、benchmark

通过门槛：

- 原文泄漏率为 0

## 9. 如何持续改进这套规则

这套规则只能靠离线验证来改，不能靠生产里自由试错。

正确顺序是：

1. 先定义失败样例
2. 再改规则
3. 再看错误率、复活率、污染率是否下降

也就是说，改进的对象是：

- 什么时候保留
- 什么时候暂存
- 什么时候隔离
- 什么时候丢弃

而不是让系统自己在生产里瞎试。
